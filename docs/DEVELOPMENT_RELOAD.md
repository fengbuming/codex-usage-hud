# 开发时让最新源码生效

本流程按需使用，不是每次修改后的必经步骤。默认完成代码和必要检查后，由用户决定是否重载、选择哪种方式，或自行手动重启。只有用户要求或当前任务已授权重载时，才运行 `tools/reload_hud.py`。工具不增加后台轮询，更新操作通过独立锁串行执行。

设置页的「管理 HUD…」将重载与退出归到一个入口，分别选择操作再确认。代理关闭时仅提供 HUD 重载，且不要求存在代理进程；不会为了重载而启动代理。失败信息保留在弹窗内，便于重试。

## 选择更新方式

| 改动 | 命令 | 正在生成的请求 |
| --- | --- | --- |
| Renderer、HUD 主程序、菜单、设置或会话逻辑 | `python tools/reload_hud.py --hud-only` | 独立代理 PID 和端口不变，继续处理 |
| 代理转发、路由、鉴权、错误信息 | `python tools/reload_hud.py --proxy-only` | 已开始的请求使用旧源码直到结束，新请求使用新源码 |
| 两部分都有改动 | `python tools/reload_hud.py --all` | 先切换代理请求处理代码，再启动新 HUD 主进程 |
| 只查看状态 | `python tools/reload_hud.py --status` | 无修改 |

`--hud-only` 会更换 HUD 主进程，HUD 界面和统计可能短暂重连；独立代理、监听端口和已有请求连接保留。`--proxy-only` 不重启代理进程，也不关闭监听端口；加载新代码期间请求仍可走旧代码，切换后新请求使用新代码。一个活跃 Codex 任务可能发出多次请求：已经开始的请求继续使用旧代码，该任务后续发出的请求会使用新代码。

代理热重载不是先断开再续接，因此无需等待“重新续上”，也不会自动重发请求或重新启动失败的 Codex 任务。新代码加载失败时保留旧代码；加载成功仍不代表新逻辑不会有运行时错误。`--all` 只是先做代理热重载，再更新 HUD 主进程，不会重启 Codex 或所有进程；代理阶段失败则不进入 HUD 阶段，HUD 阶段失败也不会自动撤销已经完成的代理代码更新。

菜单中的普通“重启 HUD”会重建运行会话，不保证刷新 Python 已导入的模块。开发工具会使用当前 Python 解释器，从当前仓库的 `src` 启动全新的 HUD 进程。工具检查 PID 身份、独立代理健康状态、HUD 设置编辑器状态，以及新进程的 HTTP 健康回执；设置编辑器打开时会停止操作，保护未保存的草稿。旧 HUD 若尚不支持开发交接命令，工具只允许停止已核验的 HUD 主 PID，始终保留代理助手。

代理助手的 TCP 监听和控制入口保持稳定。热重载先读取不可变的源码快照并预加载关键模块，成功后原子切换处理新请求的代码；旧请求及其后续延迟导入继续使用同一份旧快照。旧请求结束后回收旧代码，无需定时清理。加载失败时保持原处理代码。HTTP/SSE 连接不会为更新代码而重新建立。

## 用户选择使用工具时

1. 完成实现、必要的定向测试、编译和检查。Renderer 改动需按仓库约定更新两份派生合约。保留其他任务的工作区改动。
2. 运行 `--status`，记录代理 PID、版本、源码代次、活动请求数。使用启动 HUD 的同一 Python/venv，确认项目依赖已安装，不把临时测试依赖路径当作长期运行环境。
3. 按用户选定的方式运行对应命令。执行本工具流程时，不用 `--stop`、托盘“退出”、结束代理进程或重启 Codex 作为无感重载的替代；用户自行选择手动重启另行处理。
4. 验收代理 PID 和公共端口不变；HUD 更新要确认主 PID 已变化且新进程健康检查通过；代理更新要确认源码代次/摘要更新，新请求行为生效，原有流继续完成。
5. 只汇报实际验证结果。失败时保留代理，不自动恢复直连、不改供应商、不连续重启。HUD 启动日志在运行目录的 `development-reload.log`。

## 首次升级及控制入口改动

热重载无法倒装进尚未包含此能力的旧代理进程。遇到 `reloadSupported` 不存在/为 false 时，代理重载工具会停止并保留旧进程；HUD 主程序仍可独立更新，继续使用旧随机码 URL，不把专用鉴权头发给不识别它的旧助手。首次安装新助手需要安排一次没有生成请求的维护窗口，不得在任务执行中强杀旧助手。

`provider_proxy_service.py` 或 `provider_proxy_reload.py` 的监听/控制基础代码也不能通过请求处理代次的切换完成更新。工具会检测基础代码摘要差异并报告维护需求，不声称该部分已经热加载。后续一般代理功能修复应尽量放在请求处理模块。
